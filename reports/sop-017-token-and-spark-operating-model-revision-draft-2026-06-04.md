## 1. Core Principle

Tokens are spent to produce usable pipeline data, product artifacts, exact blockers, or controlled boundary questions.

Good token burn:
- scripts;
- runnable pipeline contracts;
- candidate rows;
- source-license lane ledgers;
- definition/reader-hint candidate packages;
- linkage/dedupe/source-route matrices;
- validators on changed inputs;
- release/package intake;
- exact Agent 6 boundary dockets.

Bad token burn:
- status-only output;
- proof-map churn when state is not stale;
- vague blockers;
- repeated validation of unchanged inputs;
- coordinator narratives that duplicate Spark or agent work;
- unauthorized acceptance claims.

## 2. What Spark Means

`Spark` is the project name for a ChatGPT model 5.3 Spark intelligence setting used on a lane. It is not the lane itself and not the whole agent. A lane may be called Agent 1, Agent 2, Agent 10, or another agent name while its intelligence/model setting is Spark.

The reason this matters operationally is token accounting: Spark-intelligence work uses a different token limit and token economics from the main executive/coordinator model lane. A Spark token issue does not automatically mean the whole agent/lane is unavailable, and it does not consume or limit Agent 13's current executive-token budget.

Spark intelligence is not a separate authority class. It is not a bypass lane, owner proxy, legal lane, QA lane, or publication lane. It does not decide source/license acceptance, Definition authority, QA acceptance, publication readiness, route publication support, public/runtime acceptance, product/data acceptance, accepted glosses, or accepted text.

When stable and explicitly enabled, Spark lanes run bounded mechanical contracts:
- exact target;
- exact input files or manifests;
- exact command or agent-authored script;
- expected output path and schema;
- validator or explicit missing-validator blocker;
- license/export lane fields where relevant;
- package owner;
- Agent 6 boundary need where relevant;
- stop condition.

If a Spark lane lacks a runnable contract, the correct state is not vague idle. The correct state is:

`awaiting_pipeline_contract` or `awaiting_changed_pipeline_contract`

with exact missing fields and paired agent owner.

Current owner correction: prior whole-agent Spark/assistant lane naming is superseded. Do not call whole agents "Sparks" as current operating language. Instead, use Spark as an intelligence/model setting on named agents. Agents set to Spark intelligence should be used perpetually for bounded production/support work when the Spark setting is stable, especially Agents 1, 2, 3, 4, and 5. If Spark intelligence glitches on a lane, the direct agent may continue under another available model/intelligence setting or return an exact blocker.

## 3. Spark Token Model

Spark-intelligence capacity is treated separately from executive/coordinator token discipline because it is a separate ChatGPT model 5.3 Spark model setting with its own token limit.

This does not mean Spark-intelligence work is unlimited. It means productive Spark token use is allowed when the task is bounded by an exact contract and produces usable pipeline data.

Spark-intelligence token burn is preferred over senior-agent or coordinator token burn for:
- counts;
- diffs;
- validators;
- inventories;
- source/license matrices;
- Definition Workbench refreshes;
- route-card dedupe;
- package-intake matrices;
- release-relevance shadow checks.

Coordinator tokens should not be spent redoing Spark work.

Current limitation: prior Spark-named whole-agent routing is suspended. Direct Agents 1-4 and Agent 10 run the work by lane name. Agents 1, 2, 3, 4, and 5 may be set to Spark intelligence for perpetual bounded work when that model setting is available and stable. A Spark-intelligence failure is a model-setting problem, not proof that the entire agent role is unavailable.

## 5. Wartime Mode

Wartime mode is compute-poor survival mode.

Use wartime mode only when compute scarcity threatens project continuation or the owner explicitly invokes wartime posture.

Wartime defaults:
- Core production continues only for highest-value artifacts.
- Overhead is starved, not allowed to become the product.
- Coordinators emit only one decision, one blocker, or one escalation.
- Sparks run only exact high-priority contracts.
- Agent 10 and the most relevant producer lanes receive priority.

Wartime question:

`If we had only enough compute for one more day, what work would I buy?`

Wartime is not the current default unless explicitly invoked.

## 8. Source And Dictionary Lane Policy

New and missed dictionaries are not presumed NC.

Old excluded dictionary rows are not presumed truly blocked.

Every source family and row subset must be lane-classified using evidence:
- `commercial_clean_candidate`
- `noncommercial_educational_candidate`
- `metadata_or_link_only`
- `blocked_or_needs_review`

NC educational rows are allowed only in a separate NC lane/export partition and must preserve:
- `derived_from_nc=true`
- `commercial_export_allowed=false`
- `attribution_required=true`
- `owner_use_attestation=noncommercial_educational_zero_profit_zero_kickback`
- `corpus_contamination=false`

Commercial-clean exports exclude NC rows by default.

## 9. Agent 1-4 Exact Task Shape

Lightweight / exact-task-mode is not a current operating mode. Agents 1-4 may be set to Spark intelligence when stable, and their work should still be exact and executable. If a model setting is weaker or cheaper, task ambiguity must be removed before routing.

`target | files | exact command/script to write or run | output artifact | schema/counts | validator | missing-field blocker | handoff owner | stop condition`

## 10. Emergency Agent-Run Mode

If an assistant lane fails, stalls, is unusable, or lacks durable standing status, the paired Agent must continue pipeline work manually.

Assistant restoration is not required for production continuation.

Failure shape:

`assistant unavailable | emergency agent-run owner | exact pipeline to continue manually | support owner | blocker`

Mappings:
- assistant-1 unavailable -> Agents 1-4/6 continue production pipeline work directly as relevant.
- assistant-2 unavailable -> Agent 10 continues release/package intake directly.
- Spark unavailable -> the paired direct Agent continues work; Spark failure is not a blocker to pipeline production.

## 11. Low-Token Output Rule

If a core lane is near its token limit, it must leave usable pipeline data.

Required low-token handoff:

`target | files used | pipeline contract state | usable counts/rows/data | next command | exact missing fields | handoff owner | Agent 6 boundary if needed | stop condition`

Minimum acceptable handoff:

`target | files | counts/rows found | next command | missing fields | handoff owner`

If usable partial pipeline data exists and the owner has explicitly re-enabled a repaired Spark lane, a Spark may continue even if one field is missing, returning:

`intermediate_pipeline_data`

with the missing field named.

## 13. SOP Revision Rule

SOPs are controlled living documents.

If actual production practice is better controlled, better evidenced, and better aligned with project success than the current SOP text, do not freeze production by default. Record a bounded SOP revision need and continue only inside the justified boundary.

Revision question shape:

`SOP issue | production impact | current controlled practice | revision needed? | exact boundary | owner | stop condition`

SOPs should make good practice repeatable, recallable, and regulator-readable. Controlled churn is acceptable when it sets up a callable pipeline state: a future restore should know the active lane, target, files, command/output shape, Agent 6 boundary, exact blocker, and stop condition without re-arguing the project frame. SOP work should not replace pipeline work; it should make pipeline work easy to resume and hard to corrupt.
