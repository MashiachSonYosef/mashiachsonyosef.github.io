# Adding a work · the runbook · 2026-08-22

What it takes to put one more work on the site, written for whoever runs it
next. Every step names its basis; the two hands-allowed places are marked.
Nothing else may be typed.

## The one-line version

Put the work's records where the pipeline reads, run the build, land what it
emits. The plan discovers works — nobody edits a list, a loop, or a page.

## What a work needs, and where it comes from

1. **A sealed identity** — corpus side, already done for 3,986 works: B/N
   rows in the identity bridge (`current-c0-location-source-bridge-*.csv.gz`)
   and its c0 rows in the gen-9 terminal. If a work is not in the bridge, it
   does not enter here; it enters through the corpus lane's admission gates.

2. **Its Y ledger fixture** (preferred) — a per-work extract in the shape of
   `data/y-genesis-navigation-v1.js`, dropped into `data/`. The plan finds it
   by shape (nodes[] with a WORK node, content_work_id, status PASS) and the
   work builds on basis SEALED_Y_LEDGER: Hebrew title, chapter labels, order,
   all the ledger's own words. The corpus lane's builder pattern for these is
   `build_y_*_navigation` (999 footsteps, ledgers/work/y/tools).

3. **Or, until the fixture lands: a typed entry** — HANDS ALLOWED, in the
   open, in `data/work-records-v1.js` under `typed_awaiting_ledger`:
   `title_en`, `c0_first`, `c0_last`, `unit_count`. Basis prints as
   TYPED_AWAITING_LEDGER on the page and the door ("awaiting its Y ledger —
   its coordinates stand typed in the open"). The plan REFUSES to build once
   both the entry and a ledger exist — landing the fixture forces the typed
   numbers out. A typed `published_as` is refused outright: addresses derive
   from the work id, always.

4. **Descriptors** — HANDS ALLOWED, plain-english usability text only, in
   `data/work-records-v1.js` descriptors: `byline`, `coord_labels`,
   `family_en`, `license_links`. No Hebrew, no numbers that exist in a
   ledger, no addresses.

5. **Serve rows** — `serves/<slug>.ndjson` from `tools/mishkan-serve-v1.mjs`,
   run against the sealed artifacts. Proven to run in the cloud container:
   the gen-9 store is sharded on work boundaries, so one work needs its one
   shard set staged (manifest + occurrences.c0c + forms.c0c + units + scripts,
   ~250 KB), the two seals, the flat shard index, the sparse runs/units/
   representations shards its ordinals touch, the rights and script catalogs,
   and the bridge. The shard list is computed from
   `terminal-compact-shard-index-v1.csv` by c0 range. (Gap, named below.)

6. **The build** — `./build.sh <mirror> <bridge.csv.gz> <serves> <stamp>`:
   plan → work-basis → serve → extract-y-nodes (fixture works) → build-zone →
   build-commentary-zone per attachment → door + stubs + redirects. Every
   stage takes its parameters from the plan. Adding a work changes no line of
   build.sh — check-build-derived fails the suite if a work-naming literal
   ever returns there.

7. **Attachments** — a pair in `data/work-records-v1.js` attachments
   (`by: "SHARED_UNIT_COORDINATES"`) seats a commentary with its base and
   builds both directions of commentary zones, each entry carrying its own
   unit's rights (basis PER_UNIT_SERVE_ROWS; one unit with two licences is
   refused, never averaged).

8. **Landing** — the GitHub web editor flow, then fetch-verify byte-identity,
   then `check-nothing-unlanded-v1` green. Commit clicks can fail silently;
   the fetch is the only truth.

## After a rollback — the first thing to run

This lane runs in a cloud container that is reclaimed without warning. The
branch survives it; the staged corpus artifacts do not. That used to cost an
hour of guess-a-file, hit-ENOENT, stage-it, guess-again — a discovery loop
run from memory, once per rollback.

The memory was the bug, so the dependency is written down on the branch:

    git clone -q --depth 1 -b gh-pages <repo> /home/claude/wk
    node tools/check-workspace-staged-v1.mjs \
      --workspace "/mnt/user-data/uploads/999 footsteps"

It reads `data/workspace-manifest-v1.json` — every corpus file this lane
needs to serve and build the published works, computed by
`plan-work-shards-v1` over the whole build plan, never typed — and prints
what is missing twice: once as a list a person can read, once as the exact
JSON array of device paths. Stage that array (in batches of 50; one file,
the COMPspan template, is 49MB and goes alone), re-run the check, and a clean
report means every serve and build in this lane can run.

The manifest is regenerated by `emit-workspace-manifest-v1` and should be
re-run from a warm workspace whenever a work is added — a work in the plan is
in the manifest the next time it runs. Two shard rows resolve only once their
runs shard is staged, so a manifest emitted cold reports fewer files than one
emitted warm; the tool says so when that happens.

## The gates that guard it

Run `tools/run-all-checks.sh` with the tree served. The reds that matter to a
new work: `check-build-derived` (plan == receipts, no literals),
`check-clean-address` (address rule, redirects, register never softens, door
Hebrew is zone-carried), `check-licence-carried` (every printed entry owns
its licence), `check-nothing-hand-typed` (no glyph typed anywhere; door
title occurrences counted), `check-frame-coverage`, `check-w-grain`,
`check-nothing-unlanded`.

## Named gaps, honestly

Closed since first writing (each with its proof):

- **Shard staging is a tool now.** `tools/plan-work-shards-v1.mjs --work
  <id>` reads the bridge, the composite shard index and the sparse binding
  index and prints the exact file list a work's resident serve needs —
  terminal shards on work boundaries, runs/representations/units shards by
  ordinal, the full sealed-oracle authority chain (~30 root files the sealed
  CLI walks before it answers), and the COMPspan template
  (`composition-map-v6/w-to-compspan-template-v6.csv.gz`, needed only for
  `--spans` parity). Proven by reproducing the hand-computed I Kings set of
  2026-08-22 exactly. Typed c0 values are read from the bridge, never from
  this tool.
- **build-zone has been exercised in the cloud container** to full content
  parity: the staged shard set + walked oracle chain served I Kings 24/24
  ids FOUND_EXACT, and `build-zone --spans` reproduced the sealed
  `i-kings.bin` content byte-for-byte (only the post-pass receipts — regloss,
  title-keys — and elapsed differ). Transport data: one 271MB file failed
  the bridge twice; 48.5MB and 49.3MB landed. Stage under ~50MB per file.
- **Commentary card heads read the Y ledger now.** `emit-work-basis-v1`
  slices each work's fixture's COMMENTARY_WORK nodes into
  `data/commentary-names-v1.json` (surface from `label_hebrew`, keys from
  `label_normalized_sequence`, refusing a node whose two fields disagree),
  and the card head prints the ledger's name where the node's `public_ref`
  equals the index the pack already carries — Rashi's card now says רש״י על
  בראשית with `data-named-by="Y-GEN-COMM-RASHI"`, three openable words.
  Works the ledger has not named keep the pack's recorded name or the open
  slot, unchanged.
- **Two of the three glyph literals** are escaped with set/string-equality
  proofs (generate-rashi-word-shards, k-normalization); the
  check-nothing-hand-typed red is now exactly `zone-lib-v1.mjs:115`, a
  held-back file — its author lands it.
